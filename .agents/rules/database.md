# Database & Migration Rules

## Purpose
Ensure relational integrity, deterministic migrations, type consistency, and safe schema evolution for Envello on Supabase PostgreSQL.

---

## 1. Schema Conventions & Types

- **Monetary Columns**: Use `NUMERIC(12, 2)` or `BIGINT` (representing integer paise). Never use `FLOAT`, `DOUBLE PRECISION`, or `REAL`.
- **Primary Keys**: Use `UUID` generated by `gen_random_uuid()` for all primary keys.
- **Foreign Keys & Constraints**:
  - All relationship columns must have explicit foreign key constraints with sensible `ON DELETE` rules (prefer `ON DELETE RESTRICT` for financial accounts to prevent accidental cascading deletion of transaction history).
  - Use `CHECK` constraints to enforce valid amounts (e.g., `amount > 0` for transaction entries) and valid status enums.
- **Audit Columns**: Every table must include:
  - `created_at TIMESTAMPTZ NOT NULL DEFAULT timezone('utc'::text, now())`
  - `updated_at TIMESTAMPTZ NOT NULL DEFAULT timezone('utc'::text, now())`
- **User Ownership**: Every user-owned table must include `user_id UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE`.

---

## 2. Versioned Migrations Discipline

- **No Manual Production DDL**: Schema changes must NEVER be executed directly in the Supabase production dashboard SQL editor without a corresponding migration file.
- **Migration Directory**: Store all migration scripts in `supabase/migrations/` ordered with timestamps (e.g. `YYYYMMDDHHMMSS_create_accounts.sql`).
- **Idempotency & Reversibility**:
  - Migrations should use `CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, and safe alterations.
  - Test both up-migration and rollback behavior in the local Supabase environment before staging.
- **No Destructive Operations**: Never drop columns or tables in production without a documented migration plan, pre-migration database backup, and verified rollback procedure.

---

## 3. Atomic Operations & Multi-Table Consistency

- **Stored Procedures / RPCs**:
  - Complex multi-row balance updates (such as an account transfer: debiting Account A, crediting Account B, and writing two ledger entries) must be wrapped in PostgreSQL functions (`SECURITY INVOKER` or audited `SECURITY DEFINER` with explicit `auth.uid()` checks).
  - All operations within an RPC execute inside an implicit transaction; any failure triggers a full rollback.
- **Indexes for Query Performance**:
  - Index all foreign keys: `user_id`, `account_id`, `envelope_id`, `transaction_id`.
  - Composite indexes on `(user_id, transaction_date DESC)` for fast ledger retrieval.

---

## 4. Test & Seed Data Discipline

- **Development Only**: Seed scripts (`supabase/seed.sql`) are for local development and integration tests only.
- **No Fake Data in Production**: Never seed fake or mockup transactions into a real user's workspace.
- **Deterministic Fixtures**: Ensure test fixtures cover edge cases: negative balances, zero-amount validations, leap years, month boundaries, and currency rounding.
